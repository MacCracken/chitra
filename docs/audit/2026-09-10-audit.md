# chitra — 2026-09-10 Security Audit (P-1 sweep; all four formats + the gate stack)

> **Status**: Fifth security audit of chitra, gating the 1.0.3 cut. The
> [2026-06-26](2026-06-26-audit.md) and [2026-06-27](2026-06-27-audit.md) audits
> covered PNG and JPEG; the [2026-08-23 P-1 sweep](2026-08-23-audit.md) re-swept
> both; the [2026-08-24 sweep](2026-08-24-audit.md) was the first line-by-line
> audit of BMP and GIF. This is a **P-1 sweep of all four formats at once**, the
> first since the 1.0.0 freeze, plus the first audit of the **gate stack itself**.
> **Date**: 2026-09-10 · **Version**: 1.0.3 (pre-tag; `chitra_version()`
> → 10003) · **Toolchain**: cyrius 6.6.2.

## 1. Scope and method

chitra is a pure-Cyrius CPU raster decode **library**: untrusted encoded bytes
in, canonical RGBA8 out. No GPU, no C shim, no external libraries, no CLI. The
threat model is unchanged — a hostile image reaches a public entry point and
attempts an out-of-bounds access, an integer overflow into an undersized
allocation, an unterminated loop, a null dereference, or silently wrong pixels.

Three things shaped this sweep, and all three are consequences of how far the
code has already been hardened:

- **10.7 million fuzz assertions** across four harnesses had already established
  that this code does not fault easily. So the search was weighted, deliberately
  and heavily, toward **silently wrong output** and toward **what a refusal
  costs** — the two classes fuzzing cannot see. That weighting is what the
  findings reflect: not one memory-safety defect was found, and the most severe
  finding is a null dereference reachable only under memory pressure.
- **The allocator never frees.** `chitra_image_free` is a documented no-op under
  the bump allocator, so every per-decode allocation is permanent for the
  process lifetime and resource amplification is **cumulative across decodes**.
  Four of the confirmed findings are refusal-path allocations; that is not a
  coincidence, it is the shape this allocator gives to the whole class.
- **The public surface has been frozen since 1.0.0.** A repair that would change
  a frozen signature is a major bump plus an ADR. None of the repairs below need
  one — but two change *behaviour* a consumer can observe, and those are called
  out explicitly in § 5.

**Method.** Eleven lenses ran over the source in parallel — integer overflow
into allocations and indices; byte-cursor and buffer bounds; the JPEG entropy
decoder; the JPEG marker parser and § A.2 scan geometry; the PNG chunk walk,
inflate and unfilter; the PNG colour/palette/tRNS pass and Adam7 geometry; BMP
headers, palette, RLE and BITFIELDS; GIF LZW, sub-blocks, GCE and frame rect;
allocation-failure, initialization discipline and error propagation; the format
router, byte budget and cross-format seams; and — new in this sweep — **the
build, gate and release machinery itself**, on the principle that a gate which
cannot fire is the same defect class as a guard which cannot fire, one level up.

Each lens was required to produce a **concrete trigger** — actual field values
and the arithmetic — not a hypothetical, and to enumerate every guard between
the public entry point and the defect. Every candidate was then put to **two
independent skeptics with opposing jobs**: one re-derived the control flow from
the entry point and read each intervening guard, the other **constructed the
malicious file byte by byte**, built a harness against it, and re-derived the
severity from scratch. A finding was accepted only if both agreed; the default
was refutation.

Of the raw candidates, **41 were confirmed by both skeptics**, **5 split them**,
and **2 were refuted**. The confirmed set deduplicates to **19 distinct
defects** — several lenses found the same BMP-RLE and GIF-allocation defects
independently, which is itself a signal about where the risk sits. Every repair
below carries a regression test that was **checked to fail against the
pre-repair code**; a test that passes both ways proves nothing, and § 4 records
what each mutation produced.

## 2. What the sweep did NOT find

Negative results are the most useful part of an audit of code that is already
hardened, so they come first.

**No memory-safety defect.** No out-of-bounds read or write reachable from a
public entry, no integer overflow into an allocation, no unterminated loop. In
particular:

- **The PNG IHDR-derived size chain is overflow-free by construction**, and its
  ordering is right. The per-side cap of 65,535 is what makes the product safe
  to compute at all: 65,535² = 4,294,836,225, nine orders below the i64 edge.
  `row_bytes` ≤ 524,280 and `pixel_size` ≤ 134,275,071 for any accepted header.
- **PNG's two-pass IDAT walk stays in lockstep**, so pass 2's copy is in bounds:
  both passes advance by exactly `4 + 4 + chunk_len + 4` per chunk, and pass 1
  errors out rather than stopping on a short tail.
- **The JPEG § A.2 scan model terminates on the coverage bitmask itself**, not
  on a proxy. No Ns/Nf/Hi/Vi combination was found in which the grid a plane is
  *sized* by and the grid its placement is *counted* by diverge.
- **GIF LZW prefix chains cannot cycle**, verified from the code rather than the
  comment: entries are only added with `prefix < the index being written`, and
  the walk is separately bounded by the dictionary size.
- **BMP per-depth source reads stay inside `stride` at every supported depth**,
  and the RLE cursor advances by ≥ 2 on every path, so the loop terminates
  structurally.
- **`src_ctype` sentinels do not collide** across the four formats.

**No wrong-output defect on well-formed input.** Differential sweeps against
external oracles — `djpeg -nosmooth` for JPEG, ImageMagick and ffmpeg for
PNG/BMP/GIF — over roughly 22,000 decode comparisons found zero disagreements
outside the three documented, deliberate divergences (`_jpeg_descale` rounding,
BMP bit replication, GIF uncovered canvas). One lens cross-checked the full
legal PNG matrix against a purpose-built **libpng** reference reader at every
dimension 1..17 with random per-row filters: 5,790 cases, byte-identical.

**Every wrong-output defect that WAS found needs a malformed or unusual file to
trigger** — which is precisely why fuzzing missed them and why the reference
cross-check is not optional coverage.

## 3. Confirmed findings and repairs

### B-1 · HIGH · `crc32_init_table()`'s OOM return discarded, and the next `crc32()` dereferences a null table

`src/png_filter.cyr:365`. sankoch allocates the 16 KB slice-by-8 CRC table on
first use and returns `-ERR_OOM` when the arena cannot supply it. chitra called
it as a bare statement. Under memory pressure `crc32_table` stayed 0 and
`_chitra_parse_ihdr`'s `crc32()` read through a null base.

⛔ **No hostile file is involved.** The trigger is arena state, so the file that
dies is the *first* PNG a memory-pressured process decodes — an ordinary valid
image. Reproduced with the repo's own 77-byte 2×2 fixture: **SIGSEGV, exit 139**,
where the documented contract is `(0, *err_out = CHITRA_ERR_OOM)`. It also
directly contradicted SECURITY.md's "every allocation is null-checked".

**Repair.** Test the return and surface `CHITRA_ERR_OOM`. `CHITRA_ERR_OOM` is
already a frozen code and `(0, *err_out set)` is already the documented
contract, so this is the behaviour the docs already claimed.

### B-2 · HIGH · A JFIF file's declared colour space was overridable by its component ids

`src/jpeg.cyr` colour decision. 0.6.1 added the correct rule that `'R','G','B'`
component ids name an RGB file (that is how `cjpeg -rgb` output is recognised
when its APP14 has been stripped). But chitra never parsed **APP0**, so nothing
in the tree knew a file was JFIF — and JFIF § 4.1 *defines* three components as
Y/Cb/Cr. The weaker rule therefore applied to files that had already answered
the question.

⛔ **Six edited bytes turn an ordinary `cjpeg` image into a whole-image colour
error with no error code**, while `chitra_image_source_color_type()` returns
0x113 and actively tells the consumer the samples are RGB. Measured on a 64×64
fixture: every colour byte wrong. `djpeg` and ImageMagick both decode the same
bytes correctly — libjpeg has never had the hole, because
`default_decompress_parms` tests `saw_JFIF_marker` **first**.

**Repair.** Parse APP0 for the five-byte `JFIF\0` identifier onto a frame flag,
and test it ahead of the Adobe transform and the component ids. The authority
order is now JFIF → APP14 transform → component ids → YCbCr, which is libjpeg's.
⚠ `cjpeg -rgb` emits **no** JFIF APP0, so real RGB files still reach rule 2 and
still report 0x113 — verified, and pinned by its own regression cell so the
repair cannot silently revert 0.6.1.

### B-3 · HIGH · JPEG component planes allocated before the amplification cap could refuse them

`src/jpeg.cyr`. GATE 2 is the honest whole-image bound, but it can only run once
every scan has decoded — by which point every plane is allocated. A 4,250-byte
file declaring 4096×4096 Nf=3 passed the per-scan GATE 1 (which tests each
component *separately* against the same span) and allocated three 16,777,216-byte
planes before GATE 2 refused it.

⚠ **50,354,832 bytes spent to return `CHITRA_ERR_DIMENSIONS`** — 11,848:1 on the
refusal path, none of it reclaimable. ~40 such files exhaust the stdlib's 2 GiB
`ALLOC_MAX`.

**Repair.** A GATE 0 before the scan loop: `total_espan` is a sum of spans inside
the file and so can never exceed `len`, which makes `w*h*4 > len * RATIO`
**strictly weaker than GATE 2**. It can only refuse what GATE 2 already refuses —
no accept/reject outcome moves — and it does not replace GATE 2, because `len`
counts bytes no scan ever reads (the 0.6.1 padding lesson). Measured after:
**22,160 bytes**, which is the per-frame table allocation and nothing else.

### B-4 · HIGH · The BMP RLE amplification cap fired after the index plane it exists to prevent

`src/bmp.cyr`. The exact cap can only run after the decode, because the only
honest denominator is the bytes actually **consumed** — an RLE stream's length is
not computable in advance. But that left a 60-byte file (4096×4096, `BI_RLE8`,
payload `00 01`) allocating *and zeroing* a 16,777,216-byte index plane first.

⚠ **16,777,344 bytes per refusal, 279,622:1**, and cumulative: 200 decodes of the
same 60 bytes reach 3.36 GB. The 0.5.3 audit named this exact defect in GIF and
repaired the GIF half; the BMP half was left, with a source comment
acknowledging the ordering and arguing the plane was "bounded by
`CHITRA_MAX_PIXELS`" — which it is, at 16.7 MB apiece on an allocator with no
free.

**Repair.** A pre-gate using `len - data_off`, an upper bound on `consumed`
(the cursor only advances and never leaves the buffer). Strictly weaker than the
exact check, so no outcome moves; the exact check stays, because padding a file
still raises the pre-gate's bound and only `consumed` sees through it. Measured
after: **128 bytes**, same error code.

### B-5 · HIGH · A latched RSTn silently zero-padded the rest of the scan while `seen_iend` reported a clean close

`src/jpeg_huffman.cyr`. `_jpeg_entropy_span` deliberately walks past RSTn
markers, so they sit *inside* the reader's span. An RSTn the decoder never asked
for — no DRI, `DRI = 0`, or the wrong interval — latched in
`_jpeg_br_load_byte`, and every subsequent bit was fabricated as zero. The latch
set `BR_MARKER` but not `BR_EOD`.

⛔ **Two bytes inserted mid-scan produce an image whose bottom is invented, with
no error and `seen_iend` = 1** — a positive assertion that the stream closed the
way the format says it should. SECURITY.md is explicit that chitra does not
raise an error for a partial JPEG, so `seen_iend` is the consumer's *only*
channel here. `djpeg` on the same bytes: exit 2, "premature end of data segment".

**Repair.** Set `BR_EOD` at the **fabrication point** — where a bit is requested
and none can be supplied — rather than at the latch. ⚠ The distinction is
load-bearing: a *legitimate* restart also latches, and `_jpeg_br_restart` then
consumes it and clears the marker without anything being fabricated. Setting the
flag at the latch would make every restart-interval JPEG report an unclosed
stream, and a companion regression cell holds that line.

### B-6 · MEDIUM · BMP RLE rejected the DWORD row padding that real encoders write

`src/bmp.cyr`. A BMP row is `w` pixels of image inside a DWORD-aligned row.
Real encoders fill the padding: a 9-pixel-wide RLE8 row comes out of ImageMagick
as nine 1-pixel runs followed by a 3-pixel run, then end-of-line, because the
uncompressed row would be 12 bytes. chitra rejected at `x >= w`.

⛔ **Every RLE BMP whose width is not a multiple of 4 failed to load.** Measured
before the repair: **30 of 30** files from `magick -compress RLE` refused with
`CHITRA_ERR_BMP_RLE`, all of which ffmpeg and ImageMagick itself read without
complaint. chitra was the outlier. The tree's own "ImageMagick-encoded RLE8"
fixture is 8×4 — a width where the padding does not exist, which is why no cell
caught it.

**Repair.** Samples in `[w, row_cap)` are **consumed and discarded**; past
`row_cap` is still refused. ⚠ The padding is not image data, so this is not
clipping — the per-write bound that stops a run painting a different image than
the file encodes is intact, and a companion cell pins the overrun rejection.
Measured after: **52 of 52** decode byte-identically to ImageMagick, and 24 of 24
RLE4 files likewise.

### B-7 · MEDIUM · The GIF LZW dictionary was allocated at the format's ceiling before a single code was read

`src/gif_lzw.cyr`. `prefix` (32,768) + `suffix` (32,768) + `chain` (4,096) =
**69,632 bytes on every call**, never memoized, on an allocator that never frees.
A 45-byte GIF paid all of it; so did one the decoder rejected on its first code.
This is the same shape 0.6.1 repaired for JPEG's tables one module over.

**Repair.** Size the dictionary to what the stream can actually reach. The bound
is arithmetic, not a heuristic: every code costs at least `min_code_size + 1`
bits and adds at most one entry, so a `data_len`-byte stream can add at most
`data_len * 8 / (min_code_size + 1)` entries. ⚠ `table_cap` replaces the flat
ceiling at **every** bound — the `next_code` ceiling and both chain-walk bounds
— because a guard one looser than the array it protects is the exact defect the
0.5.3 sweep found in this file. Measured: **69,776 → 416 bytes** for a small
GIF; 20 differential cases against ImageMagick byte-exact; 1,379,514 fuzz
assertions clean.

### B-9 … B-17 · the gate stack

The eleventh lens audited the machinery that is supposed to catch everything
above. It found that several gates could not fire:

- **B-9 · HIGH · `scripts/check-surface.sh` ran nowhere.** CLAUDE.md and
  public-surface.md both say the frozen-surface gate runs on "every `make
  lint`" — and it does, but **CI re-implements the lint loop** rather than
  calling `make lint`, so the one machine that blesses a tag never ran it. At
  v1.0 an unclassified new export is a compatibility promise made by accident.
  *Repair:* an explicit CI step.
- **B-10 · MEDIUM · The toolchain pin was extracted with an unvalidated grep.**
  A reformatted, renamed or missing pin line yields an **empty**
  `CYRIUS_VERSION`, and `install.sh` treats that as "give me the latest
  release" — CI would go green on a toolchain nobody pinned, which is exactly
  what "the pin is the only source of truth" exists to prevent. *Repair:*
  validate the extraction as semver in both workflows, fail loudly otherwise.
- **B-11 · MEDIUM · CI's dist-sync gate ignored `dist/chitra.deps`.** `cyrius
  distlib` writes both artifacts and `cyrius deps` treats the sidecar as
  authoritative for every consumer, so a stale leaf list could drift green.
  *Repair:* diff both.
- **B-12 · MEDIUM · No test could tell width from height on the four frozen
  `_rgba8` wrappers.** Every wrapper cell used a **square** fixture, so
  transposing the two stores in `chitra_png_decode_rgba8` — mabda's primary
  entry point — passed all 13 suites, all 3,035 assertions and all 10.7 M fuzz
  assertions with nothing red. Verified by doing exactly that. *Repair:*
  non-square fixtures for all four, cross-checked against the full decoder's
  accessors. Post-repair, the same mutation fails in five suites.
- **B-13 · MEDIUM · `check-anchors.sh` inspected 66 of ~126 line-number claims
  and reported "suspicious: 0".** Its regex matched only citations that repeat
  the filename, so the bare `:NNN` continuation shorthand the ADRs use most was
  invisible — including anchors landing on a bare brace, the exact case the
  script advertises catching. *Repair:* resolve bare anchors against the last
  filename named in the same document. Coverage 66 → **90**, which immediately
  surfaced **5 rotted anchors**, all now repaired.
- **B-14 · LOW · `version-check.sh`'s manifest arm could not fire**, and its
  guard also passed a manifest that had *lost* its version key. *Repair:* decide
  the template form, the literal form and the unrecognised form explicitly; an
  unrecognised form is now a FAIL. All three arms proven reachable.
- **B-16 / B-17 · LOW · Two scripts' failure-reporting branches were
  unreachable** under `set -euo pipefail`: the very command substitution that
  was supposed to feed the diagnostic aborted the script first. So a red suite
  exited 1 with no indication of which suite, and `bench-csv.sh`'s two "refusing
  to record numbers" guards — the ones that keep a failed run out of the
  committed series — could never run. *Repair:* capture the status instead of
  letting `set -e` eat it.

## 4. Mutation results

Every repair's regression test was run against the pre-repair code. A test that
passes both ways proves nothing, so this is what each produced:

| finding | mutation | pre-repair result |
|---|---|---|
| B-1 | restore the bare `crc32_init_table();` | suite **SIGSEGV**, never reached a verdict |
| B-2 | bypass the JFIF check | `got 275 (0x113), expected 259 (0x103)` |
| B-3 | delete GATE 0 | cost assertion fails; verdict and code unchanged |
| B-4 | delete the pre-gate | cost assertion fails; verdict and code unchanged |
| B-5 | restore `if (cnt == 0) { return 0; }` | `seen_iend got 1, expected 0` |
| B-6 | restore the `x >= w` bound | padded-row fixture refused |
| B-7 | restore the flat dictionary ceiling | cost assertion fails |
| B-12 | transpose w/h in all four wrappers | **5 suites** fail (was 1) |
| B-14 | — | all three arms fire on a broken manifest |

⚠ Four of these are **cost** assertions, and they have to be: B-3, B-4 and B-7
do not change any verdict or error code, only what reaching it costs. Asserting
the refusal alone would pass against both versions, which is the whole reason
these defects survived four prior audits.

## 5. Behaviour a consumer can observe

Two repairs change what a caller sees on inputs that previously "worked", and
both are narrowings toward the reference decoders rather than surface changes.
Neither touches a frozen signature, name, record offset or error code.

- **B-5** changes `chitra_image_seen_iend()` from 1 to 0 for a JPEG whose scan
  contains an unexpected RSTn. A consumer keying on `seen_iend` will newly see 0
  for such files — which is the point: they were being told a fabricated image
  had closed cleanly.
- **B-2** narrows which files report `source_color_type` 0x113. The sentinel and
  its meaning are unchanged; the set of files that qualify is now libjpeg's.
- **B-6** *widens* acceptance: files previously refused with
  `CHITRA_ERR_BMP_RLE` now decode. Nothing that decoded before decodes
  differently.

## 6. Accepted risk, and what was deliberately not changed

- **The uncapped logical-screen canvas in GIF** remains accepted risk, as
  0.5.3 recorded. A hostile GIF naming a 4096×4096 canvas and a 1×1 frame is
  capped at 64 MB rather than rejected, because a large canvas painted by a
  small first frame is the *normal* shape of an optimised animation — the bomb
  and the legitimate file are the same file shape, and a ratio cannot separate
  them.
- **sankoch's 16 MiB `DECOMPRESS_MAX_OUTPUT`** is not raised. 2.7.13 added
  `zlib_decompress_capped`, which would let a caller that has independently
  bounded its output name its own ceiling — chitra still calls plain
  `zlib_decompress`. Adopting it retires files that currently answer
  `CHITRA_ERR_INFLATE_LIMIT`, so it is a release with an entry, not a swap.
- **`CHITRA_MAX_RAW_BYTES` is unreachable at every output-size site**, because
  `CHITRA_MAX_PIXELS` binds tighter in all four formats. The caps are left in
  place as a backstop against a future widening of the pixel cap, and the docs
  that advertised them by line number are corrected rather than the code.
- **The 11 `untracked deferral` lint diagnostics are all false positives** on
  prose keywords (most starkly a comment reading "PERMANENTLY, **not
  deferred**"). `--strict-deferrals` is left off, and the flag's
  argument-order sensitivity — `cyrius lint <file> --strict-deferrals` silently
  drops it and exits 0 — is recorded in `state.md` so nobody believes the strict
  gate ran when it did not.

## 7. Status after this audit

**19 distinct defects repaired**, every one with a mutation-checked regression
test. **3,084 test assertions** across 13 suites and **10,732,113 fuzz
assertions** across 4 harnesses, 0 failures. The full decode matrix was
re-verified against `djpeg -nosmooth`, ImageMagick, ffmpeg and a purpose-built
libpng reference reader.

The sweep found **no memory-safety defect and no wrong-output defect on
well-formed input**. What it found instead was a cluster of **refusal-path
allocations** — four of them, in three formats — and a cluster of **gates that
could not fire**. Both clusters are consequences of the same thing: this code
has been hardened against the inputs that crash it, so what is left is what a
*refusal* costs and whether the machinery watching for regressions is actually
watching.

⇒ **The lesson carried forward**: a cap belongs before the allocation it exists
to prevent, and when its honest denominator is only knowable afterwards, it
needs a second, strictly weaker bound in front. Three of the four repairs in
that cluster have exactly that shape, and the fourth (B-7) removes the
allocation's dependence on the format's ceiling entirely.
