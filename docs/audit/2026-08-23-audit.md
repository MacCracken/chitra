# chitra — 2026-08-23 Security Audit (P-1 sweep; both decode paths + first fuzz harnesses)

> **Status**: Third security audit of chitra, gating the 0.3.3 cut. The
> [2026-06-26 PNG audit](2026-06-26-audit.md) verified the PNG decoder's
> fork-parity with kii; the [2026-06-27 JPEG audit](2026-06-27-audit.md)
> covered the then-new baseline JPEG decoder. This audit is a **P-1 sweep of
> both paths at once** — ten adversarial lenses over every module, each
> finding put to two independent skeptics before it was accepted — plus the
> repair of everything confirmed and the addition of chitra's **first in-tree
> fuzz harnesses** and its **first benchmark harness**, which together close
> **both** remaining v1.0 hardening gates.
> **Date**: 2026-08-23 · **Version**: 0.3.3 (pre-tag; `chitra_version()`
> → 303) · **Toolchain**: cyrius 6.5.35.

## 1. Scope and method

chitra is a pure-Cyrius CPU raster decode **library**: untrusted encoded
bytes in, canonical RGBA8 `ChitraImage` out. No GPU, no C shim, no external
libraries, no CLI. The threat model is unchanged from the prior audits — a
hostile PNG or JPEG reaches a public entry point and attempts an
out-of-bounds access, an integer overflow into an undersized allocation, an
unterminated loop, a null dereference, or silently wrong pixel output.

Two properties make chitra's exposure sharper than a typical decoder's, and
both shaped this sweep:

- **The allocator never frees.** `chitra_image_free` is a documented no-op
  under the bump allocator, so any per-decode allocation is permanent for the
  process lifetime. Resource amplification is therefore cumulative across
  decodes, not per-decode — a consideration that produced finding **H-2**.
- **JPEG has no checksum.** PNG verifies a CRC-32 on every chunk, so a
  malformed chunk is caught before interpretation. A JPEG scan has nothing of
  the kind: every entropy byte is attacker-chosen and only chitra's own bounds
  stand between it and the decode loop.

**Method.** Ten lenses were run over the source in parallel — integer
overflow into allocations/indices, byte-cursor and buffer bounds, the JPEG
entropy decoder, the JPEG marker/segment parser, the PNG chunk walk +
inflate + unfilter, the PNG color/palette/tRNS pass, Adam7 deinterlace
geometry, allocation-failure and initialization discipline, error
propagation, and JPEG plane placement / upsample / color conversion. Each
lens was required to produce a **concrete trigger** (actual field values and
the arithmetic), not a hypothetical. Every candidate finding was then put to
**two independent skeptics** with opposing jobs: one re-derived the control
flow from the public entry point and enumerated every guard in between, the
other constructed the malicious file byte-by-byte and re-derived the
arithmetic and severity from scratch. A finding was accepted only if both
agreed. Findings were additionally hand-verified against the source before
repair, and every repair carries a regression test that was **checked to fail
against the pre-repair code** — a test that passes both ways proves nothing.

Of the raw candidates, **11 were confirmed**, **3 split the skeptics**, and
**11 were refuted** (several of the latter only because the repair had
already landed while verification was still running).

## 2. What the sweep did NOT find

Negative results are the most useful part of an audit of code that is already
hardened, so they are recorded first. The following were examined closely and
found **correct**:

- **The JPEG entropy bounds.** DC magnitude category rejected above 11, AC
  size above 10, and the coefficient index checked against 63 before the
  block write (`jpeg_huffman.cyr`). `DECODE` caps the code length at 16 and
  bounds the resulting symbol index in both directions, so an incomplete or
  over-subscribed table cannot index outside the symbol list. Every loop in
  the entropy path provably advances or exits: past end-of-data the bit
  reader returns zero bits, `DECODE` terminates on the length cap, and the AC
  loop always increases `k` or sets EOB.
- **Adam7 geometry.** `_chitra_adam7_inflated_size` and the consumption walk
  in `_chitra_deinterlace` use the *same* helpers, the same `pw > 0 && ph > 0`
  guard and the same `(pw * bpp_bits + 7) / 8` row formula, so the size the
  cap was computed from is exactly the size the walk consumes. No mismatch,
  and therefore no short read or overread.
- **JPEG plane writes.** The MCU block write index reaches exactly
  `cph * cpw - 1` at the last block of the last MCU — in bounds, with no
  slack. The box-upsample source index is bounded because
  `mcu_rows * v_i * 8 >= h * v_i / max_v` by construction.
- **Signed-shift discipline.** Cyrius `>>` is *logical*, which silently
  corrupts negative values. Every `>>` in the tree was checked: all operate on
  non-negative byte values, and the IDCT correctly routes its signed
  round-to-nearest division through `_jpeg_descale`. No raw shift on a signed
  intermediate slipped through.
- **Palette and span discipline.** Palette indices are hard-rejected against
  the real PLTE entry count, and the PLTE/tRNS spans are re-validated against
  `(src, len)` before being dereferenced in the color pass.
- **Unfilter predictors.** All five § 9 predictors bound their left/up-left
  neighbour reads by `i >= bpp`, and both the non-interlaced and Adam7 paths
  explicitly zero their prev-row buffers rather than relying on the
  allocator's fresh-page behaviour.

No memory-safety defect — no OOB read, OOB write, or integer overflow into an
allocation — was found or is repaired below. Every confirmed finding is a
correctness, conformance, resource, or defence-in-depth issue.

## 3. Confirmed findings and repairs

Severity follows the project scale: CRITICAL (remote / privilege escalation),
HIGH (moderate effort), MEDIUM (specific conditions), LOW (defence in depth).

### H-1 · MEDIUM · Depth-16 tRNS color key compared at the wrong width

`src/png_color.cyr` — color types 0 and 2.

chitra reduces 16-bit samples to their high byte for its RGBA8 output, and
the tRNS comparison was performed **at that reduced width**. The spec keys one
exact sample value (§ 11.3.2); comparing high bytes keys all 256 values that
share one — and for truecolor, all 2^24 that share the three. A grayscale
image with tRNS `0x1234` also rendered `0x1200`–`0x12FF` transparent.

**Repair.** The key and the sample are now both assembled at full 16-bit
width before comparison. At depth 8 this is identical behaviour (the key's
high byte is 0), except that an out-of-range key now correctly matches
nothing instead of aliasing onto its low byte.

**Regression.** `test_decode_gray16_trns_no_high_byte_alias` — a 3×1 gray16
image whose pixels are `0x1234` (the key), `0x12FF` and `0xFFFF`. The first
two reduce to the *same* 8-bit output, so only a full-width comparison can
tell them apart. Verified to fail against the pre-repair code
(`px1` returned alpha 0 instead of 255).

### H-2 · MEDIUM · No output:input amplification cap on the JPEG path

`src/jpeg.cyr` — decode scan entry.

The PNG path bounds inflate output against IDAT input at
`CHITRA_MAX_INFLATE_RATIO` (1100:1). The JPEG path had **no analogue**, and
needs one *more* than PNG does: the entropy bit reader zero-pads past
end-of-data, so a hostile file needs no scan payload at all — the declared
SOF0 geometry alone drives the work. A ~150-byte file declaring 4096×4096
allocates ~67 MB of RGBA plus planes and runs hundreds of thousands of IDCT
blocks. Because the bump allocator never reclaims, a handful of such files
exhausts a long-running consumer (mabda decodes images into GPU textures).

This was **demonstrated empirically**, not merely argued: with the cap
disabled, a 150-byte fixture decodes to a full 4096×4096 image.

**Repair.** `CHITRA_MAX_JPEG_RATIO` (4096:1), checked as
`w * h * 4 > len * ratio` before any plane is allocated. Capping the RGBA
output bounds the planes too — they sum to under 1× the RGBA buffer for every
supported sampling. The ratio leaves roughly 6× headroom over the most
compressible *real* image (a maximally flat 4096×4096 JPEG still carries
about 2 bits per block, ~685:1) while rejecting the geometry-only bomb by
three orders of magnitude.

**Regression.** `test_reject_jpeg_amplification_bomb` (rejects with
`CHITRA_ERR_DIMENSIONS`) **and** `test_amplification_cap_allows_real_images`,
which asserts both real fixtures still decode — a cap that rejects
legitimate images would be a worse bug than the one it fixes.

### H-3 · MEDIUM · Single-component scans decoded with interleaved MCU geometry

`src/jpeg.cyr` — decode scan geometry.

T.81 § A.2 makes a scan carrying a **single** component non-interleaved: the
MCU is one 8×8 data unit, over the component's own sample dimensions. chitra
computed the interleaved geometry (MCU = `max_h × max_v` data units)
unconditionally. For the only component, `max_h` *is* that component's `H`,
so the two layouts coincide exactly when `H = V = 1` — which is what every
real grayscale encoder emits, and what all existing fixtures used. They
diverge as soon as `H > 1` or `V > 1`: at `w = 24, H = 2` chitra pulls 4
blocks where T.81 wrote 3. The surplus blocks are zero-padded by the bit
reader, so the image decodes to fabricated content with no error raised; with
DRI present the restart counter also counts the wrong units and rejects a
well-formed file.

Memory-safe throughout — the plane is sized from the same geometry — but the
decoder disagrees with libjpeg and ImageMagick on a spec-legal input class,
which breaks the reference-parity claim.

**Repair.** chitra does not implement the non-interleaved layout, so it now
**rejects** rather than mis-renders, with `CHITRA_ERR_UNSUPPORTED` — the same
defer-don't-half-implement posture already applied to the non-baseline SOF
modes, and a direct application of *correctness is the optimum sovereignty*.
Implementing the layout properly is recorded as future work.

**Regression.** `test_reject_single_component_noninterleaved`, verified to
fail against the pre-repair code.

### H-4 · MEDIUM · `chitra_err_new` inverted its own contract on allocation failure

`src/error.cyr`.

The 16-byte allocation backing every `ChitraErr` was unchecked. On failure
this was wrong twice over: it stored through a **null pointer**, and the
function returned **0** — which every caller reads as *no error*, inverting
the failure contract at the exact moment a failure must be reported. This sat
on every error path in the library, including the OOM path itself.

**Repair.** A BSS-resident fallback `ChitraErr` with no allocation
dependency. `chitra_err_new` now never returns 0. Last-writer-wins on a shared
record is an acceptable trade once the heap is gone; a live, correctly-coded
error beats both a fault and a silent success. This repair also dissolves a
separate reported concern about `chitra_jpeg_decode` gating on `*err_out`,
since a null `ChitraErr` is no longer reachable.

### H-5 · LOW · Entropy bit reader did not skip 0xFF fill-byte runs

`src/jpeg_huffman.cyr`.

T.81 § B.1.1.2 allows any marker to be preceded by any number of `0xFF` fill
bytes. The entropy reader treated the second `0xFF` of such a run as a marker
code, so a well-formed restart stream written as `FF FF D0` was seen as
"marker 0xFF" and `_jpeg_br_restart` rejected a **valid file**. Notably the
header marker walk already collapsed fill runs correctly — only the entropy
side was missing the same handling, an asymmetry this repair closes.

**Repair.** The fill run is collapsed in `_jpeg_br_load_byte`, leaving the
position on the last `0xFF` where restart resync expects it, and
`_jpeg_br_restart` skips the same run defensively.

### H-6 · LOW · ZRL overrun reported a corrupt block as a clean decode

`src/jpeg_huffman.cyr`.

An AC run-length ZRL fills coefficients `k..k+15`. Running that past index 63
is exactly as corrupt as the ordinary run overrun immediately below it —
which *was* rejected — but the ZRL path simply fell out of the loop as a
successful decode.

**Repair.** ZRL now rejects with `CHITRA_ERR_JPEG_ENTROPY` when the run ends
outside the block, matching its sibling.

### H-7 · LOW · Marker classifier treated non-segment markers as length-bearing

`src/jpeg_markers.cyr`.

SOI (`0xD8`), the `0x00` stuffing byte, and the entire T.81 Table B.1
reserved range (`0x02`–`0xBF`) fell through to "length-bearing, skip". The
walk then read the next two stream bytes as a segment length and skipped that
far — a parser desync steered entirely by attacker bytes. Bounds-checked, so
not an overread, but it can jump the cursor over a real segment.

**Repair.** All three classes now reject with `CHITRA_ERR_JPEG_MARKER`.

**Regression.** `test_reject_nonsegment_markers`, five cases across the
range; pre-repair they returned `CHITRA_ERR_TRUNCATED` instead.

### H-8 · LOW · PNG chunk-ordering guards were incomplete

`src/png_filter.cyr`. Three related gaps in the chunk walk:

1. **PLTE-after-IDAT was defeated by a zero-length IDAT.** The ordering guard
   tested `idat_total > 0`; a spec-legal empty IDAT adds nothing to the total,
   so prefixing one let a late PLTE through. Now tracked by an explicit
   `seen_idat` flag.
2. **tRNS had no ordering or duplicate guard at all**, unlike its sibling
   PLTE. A second tRNS silently overwrote the first captured span, and a
   post-IDAT tRNS was honoured against already-committed pixel data. Both now
   reject (§ 5.6 / § 11.3.2).
3. **Unknown *critical* chunks were silently skipped.** § 5.4 requires a
   decoder that does not recognise a critical chunk to abort — the chunk by
   definition changes how the image is to be interpreted, so skipping it means
   rendering a stream whose meaning the decoder demonstrably does not
   understand. Now rejected via the ancillary bit with
   `CHITRA_ERR_UNSUPPORTED`.

**Regression.** Four rejection tests, all verified to fail pre-repair, plus
**`test_unknown_ancillary_chunk_still_decodes`** as a deliberate control:
§ 5.4 rejection must not become blanket rejection, so an unknown *ancillary*
chunk must still be skipped and the image must still decode. That control
passes both before and after, which is exactly what makes it a control.

### H-9 · LOW · Constant data and uninitialized table storage

Two defence-in-depth items:

- **`src/jpeg_idct.cyr`** — the zig-zag map was built into an unchecked
  `alloc(512)`, writing 64 values through a null pointer on failure. Constant
  data has no business owning a failure mode: it now lives in BSS, removing
  the allocation entirely.
- **`src/jpeg_markers.cyr`** — Huffman table storage was allocated but never
  zeroed, unlike the quant storage beside it. The `JF_HUFF_PRESENT` bitmask
  already gates every selector against a table a DHT actually defined, so this
  was not a live bug, but the asymmetry is now closed.

## 4. Split decisions and accepted risk

- **`CHITRA_MAX_RAW_BYTES` caps in the JPEG path are unreachable.** Correct:
  `CHITRA_MAX_PIXELS` (16,777,216) bounds the geometry well below
  `CHITRA_MAX_RAW_BYTES` (268,435,456), so those comparisons cannot fire. They
  are **retained deliberately** — a redundant bound costs nothing and remains
  correct if either ceiling is ever retuned. Recorded here so the redundancy
  is not mistaken for coverage.
- **`png_color.cyr` allocates the output buffer before palette validation.**
  Accepted. The allocation is already bounded by the dimension caps, and
  reordering would trade a bounded early allocation for a more tangled
  validation path.

## 5. Fuzz harnesses (new)

`make fuzz` (`cyrius fuzz`, globbing `fuzz/*.fcyr`) is chitra's first in-tree
adversarial-input harness and closes the first of the two v1.0 hardening
gates. It
asserts **two** invariants, not one:

1. **Survival** — the decoder returns on any byte sequence: no fault, no
   corruption, no unterminated loop.
2. **Contract** — the documented result shape holds on every path: failure
   returns 0 *and* sets `*err_out` to a non-zero `ChitraErr` with a printable
   name; success returns a coherent image and leaves `err_out` at 0.

The second is what a crash-only fuzzer misses, and it matters here: mabda maps
`ChitraErr` straight onto `GpuErr`, so a failure that forgets to set the error
hands a consumer a stale or zero code.

| harness | cases |
|---|---|
| `fuzz/fuzz_png.fcyr` | random bytes; **valid signature + random chunk stream**; bit-flipped valid fixture; full truncation sweep; degenerate/negative lengths |
| `fuzz/fuzz_jpeg.fcyr` | random bytes; **SOI + random marker stream**; bit-flipped fixture; truncation sweep; **entropy-segment-only mutation** against both the hand-built 8×8 and the real ImageMagick 16×16 gradient; degenerate/negative lengths |

The signature-prefixed and entropy-only cases are the high-value ones: they
keep the header valid so hostile bytes reach the chunk walk and the
bit-reader/`DECODE` path directly rather than being turned away at the
signature gate.

`fuzz_jpeg` opens with a **harness self-check** — it asserts both fixtures
decode clean, that SOS is actually located, and that the entropy span is wide
enough for mutation to mean anything. This exists because the first draft of
the harness silently exercised only a 4-byte entropy span; a fuzz harness that
no-ops is worse than none, so the harness now proves it is doing work before
it claims to.

**Result: ~1,000,000 decode cases / 3,464,838 assertions, 0 failures**, in
about 10 seconds of wall clock — which clears the roadmap's *10⁶ iterations
clean* v1.0 criterion, not merely the "a harness exists" bar. The harnesses
found no defect —
consistent with the negative results in § 2, and the reason no repair above
originates from fuzzing.

## 6. Benchmark harness (new)

`make bench` (`cyrius bench tests/bcyr/chitra.bcyr`) closes the second v1.0
gate. It is included in this report because it shares the fuzz harness's
central discipline: **the harness must prove it is measuring the thing it
claims to measure.**

chitra's in-tree *test* fixtures are 2×2 to 16×16 — correctly so, since a
test wants a known answer, not a workload. Timing those would report
allocation, header parse and table-build overhead and label it throughput. So
the harness **generates** its fixtures at 256×256:

- **PNG** — real scanlines pushed through sankoch's `zlib_compress`, so the
  decode side runs the genuine inflate + unfilter path rather than a
  stored-block shortcut. Adam7 fixtures are interleaved using chitra's *own*
  pass-geometry helpers (`_adam7_xs` / `_ys` / `_xstep` / `_ystep`), so the
  generator and the decoder cannot disagree about the layout.
- **JPEG** — no encoder exists in the dependency set, so the harness writes
  the scan: an MSB-first bit writer with the mandatory `0xFF` stuffing, the
  Annex K.3.1 DC luminance table and a compact AC table, emitting real DC
  **and** AC coefficients per block so `DECODE` / `RECEIVE` / `EXTEND`
  actually execute instead of hitting EOB immediately.

**Every generated fixture is decode-verified against the generator before it
is timed**, and a verification failure aborts the run rather than reporting a
number. This was confirmed by sabotaging the chunk CRC: the run reported
`VERIFY FAIL` per fixture, exited non-zero, and `scripts/bench-csv.sh`
refused to record the results.

First recorded baseline (this host, 256×256 = 65,536 px, minimum of 20
rounds): JPEG grayscale **43 ns/px**, PNG rgba8 **83 ns/px**, JPEG 4:2:0
**91 ns/px**, PNG Adam7 rgba8 **128 ns/px**, JPEG 4:4:4 **145 ns/px**, PNG
palette8 **154 ns/px**. Fixed cost at 16×16: PNG **60 µs**, JPEG **16 µs**.
Adam7 costs ~54 % over the equivalent non-interlaced decode.

Benchmarks are a **performance** signal, not a security one, and are
deliberately excluded from `make test-all`: the numbers are host- and
load-dependent, so gating a correctness run on them would only manufacture
flakes.

## 7. Status after this audit

| gate | result |
|---|---|
| `make test` | **784 assertions, 0 failures** across 5 suites |
| `make fuzz` | **3,464,838 assertions, 0 failures** over ~10⁶ decode cases |
| `make lint` / `fmt-check` / `vet` | clean (both gates now also cover `fuzz/*.fcyr`) |
| `make version-check` | consistent across all five sources of truth |
| `cyrius check --with-deps dist/chitra.cyr` | compiles clean |
| `make bench` | 12 benchmarks, every fixture self-verified, ~2 s |

**Both v1.0 hardening gates close in this cut**: the in-tree fuzz harness at
10⁶ iterations clean (~1,000,237 cases, 0 failures), and the benchmark
harness with committed CSV history — see § 7. What now stands between chitra
and a v1.0 freeze is the API/ABI freeze itself, not hardening infrastructure.

Future work identified but deliberately not taken in a patch release:

- Implement the T.81 § A.2 non-interleaved layout so single-component scans
  with non-unit sampling factors **decode** instead of being rejected (H-3).
- Reword the `chitra_err_name` strings for `CHITRA_ERR_INTERLACE` and
  `CHITRA_ERR_BIT_DEPTH`, which still read as capability limits when both are
  validity rejections. This changes public output, so it belongs to the v1.0
  API freeze.
- Add `@public` markers to `chitra_png_check_signature` and
  `chitra_jpeg_check_signature`, which are public by documentation and
  consumer use but carry neither the file-level nor the per-function marker.
