# chitra — 2026-08-24 Security Audit (P-1 sweep; first audit of BMP and GIF)

> **Status**: Fourth security audit of chitra, gating the 0.5.3 cut. The
> [2026-06-26](2026-06-26-audit.md) and [2026-06-27](2026-06-27-audit.md)
> audits covered PNG and JPEG; the [2026-08-23 P-1 sweep](2026-08-23-audit.md)
> re-swept both. This is the **first line-by-line audit of BMP and GIF**,
> which shipped across 0.4.0–0.5.2 with known-answer suites, reference
> cross-checks and heavy fuzzing but no guard review.
> **Date**: 2026-08-24 · **Version**: 0.5.3 (pre-tag; `chitra_version()`
> → 503) · **Toolchain**: cyrius 6.5.35.

## 1. Why this audit, and what it assumed

The 0.5.2 cut alone surfaced **two silent bugs in BMP** that months of fuzzing
had not: channel widening used arithmetic where the correct mapping is bit
replication (shifting every 16-bit pixel's color), and a depth predicate
written as `bpp < 24` had been a safe shorthand for "indexed" and quietly
stopped being one when 16 bpp was added. Neither was a crash. Both were
**wrong output**.

That set the sweep's premise: the fuzzers have already established that this
code does not fault easily — 7.4 M assertions across four harnesses say so —
so the remaining risk is concentrated in defects that produce a plausible
image rather than a crash. Ten adversarial lenses ran with that weighting,
each finding put to two independent skeptics (one re-deriving the control flow
from the entry point, one constructing the file byte-by-byte).

Of the raw candidates, **9 were confirmed**, **5 split the skeptics**, and
**14 were refuted**. Every confirmed finding is repaired below, and several
were found independently while the sweep was still running — noted where so.

## 2. What the sweep did NOT find

No memory-safety defect. No out-of-bounds read or write reachable from a
public entry, no integer overflow into an allocation, no unterminated loop.
The following were examined closely and are correct:

- **GIF interlace geometry.** The four passes (starts 0/4/2/1, steps 8/8/4/2)
  partition the rows exactly — every residue mod 8 is covered once — so the
  source-row counter cannot exceed the decoded index plane.
- **LZW prefix chains cannot cycle.** Entries are only ever added with
  `prefix < the index being written`, verified from the code rather than the
  comment, so chains strictly decrease.
- **BMP per-depth source reads** stay inside `stride` at every supported depth
  (the 4-byte row padding gives 24 bpp its slack, and 16/32 bpp land exactly).
- **BMP branch predicates** are exhaustive over `{1,4,8,16,24,32}` — no depth
  reaches the pixel loop without a branch, so no output pixel is left at
  whatever the allocator returned.
- **`src_ctype` sentinels do not collide.** PNG's raw color types are ≤ 6;
  JPEG's are `0x100 | ncomp`, BMP's `0x200 | bpp`, GIF's `0x300 | mcs`.
- **No PNG/JPEG regression.** All nine 2026-08-23 repairs (H-1 … H-9) are
  present and intact; growing the router from two formats to four did not
  change routing for any PNG or JPEG input.

## 3. Confirmed findings and repairs

### A-1 · MEDIUM · 32-bpp `BI_BITFIELDS` masks parsed, validated, then ignored

`src/bmp.cyr` — the 32-bpp pixel path. *(Found independently mid-sweep.)*

The mask path was entered only when an **alpha** mask was present. A 32-bpp
`BI_BITFIELDS` file declaring R/G/B masks but no alpha mask fell through to a
fixed B,G,R byte read and silently ignored its own masks. A file whose red
mask is the low byte decoded **with red and blue swapped** — confirmed against
ImageMagick, which returns `(200,100,50)` where chitra returned `(50,100,200)`.

**Repair.** Masks govern both packed depths unconditionally. Whether the file
also declares alpha is now a separate question. For `BI_RGB` the header fill
supplies the documented default masks, and those reproduce the byte-order read
exactly (`0x00FF0000 >> 16` is the same byte as `srow + x*4 + 2`), so this is a
unification rather than a behaviour change for anything but the bug.

### A-2 · MEDIUM · Mask fields honoured under `BI_RGB`, rendering images invisible

`src/bmp.cyr` — header parse.

Microsoft is explicit that `bV4RedMask` and friends are *"valid only if
compression is BI_BITFIELDS"*, and real writers populate them anyway under
`BI_RGB`. chitra read them whenever the header was V2 or later. Combined with
A-1's alpha handling, a V4 `BI_RGB` file with a stale alpha mask over padding
bytes decoded **fully transparent** — the entire image invisible. ImageMagick
returns it opaque.

This predates 0.5.3: 0.5.2 had the same trigger.

**Repair.** Mask fields are read only under `BI_BITFIELDS` /
`BI_ALPHABITFIELDS`. Under `BI_RGB` the documented defaults are the only source
of layout.

### A-3 · MEDIUM · `BI_RGB` defaults injected into bitfields files, making a guard unreachable

`src/bmp.cyr` — header parse.

The default masks were applied to *any* file whose colour masks were all zero,
including a `BI_BITFIELDS` file that declared none. That invented a layout the
file never stated — and, worse, made the **"at least one colour channel"**
guard **unreachable dead code**, because the defaults erased exactly the
condition that guard tests. The 0.5.2 CHANGELOG claimed that guard rejects such
files; it could not fire, so the claim was false and no test could cover it.

**Repair.** Defaults apply only when `is_bitfields == 0`. A bitfields file
declaring no colour channel now rejects with `CHITRA_ERR_BMP_MASK`, and the
regression test proves the guard reachable.

### A-4 · MEDIUM · No amplification cap on BMP-RLE or GIF

`src/bmp.cyr`, `src/gif.cyr`. *(Found independently mid-sweep.)*

PNG bounds inflate output against IDAT input; JPEG has had an output:input cap
since 0.3.3. Neither newer format got one. Demonstrated, not argued: a
**1,082-byte** RLE8 file and a **797-byte** GIF each declaring 4096×4096
decoded into ~64 MB that the bump allocator never reclaims.

**Repair.** `CHITRA_MAX_BMP_RLE_RATIO` (4096:1) and `CHITRA_MAX_GIF_RATIO`
(16384:1), both sized against the format's own best case rather than picked
round:

| | legit min input for a solid 4096×4096 | cap floor | headroom |
|---|---|---|---|
| BMP RLE | ~137 KB (a 2-byte opcode encodes ≤ 255 px) | 16 KB | 8.5× |
| GIF LZW | ~13 KB (one dictionary cycle ≈ 7.4 M px in 5.8 KB) | 4 KB | 3.2× |

The GIF cap is deliberately looser than PNG's 1100:1, and the reason is worth
stating rather than hiding in a round number: **LZW's legitimate compression of
degenerate content is close to the bomb ratio.** It bounds the extreme case,
not the merely aggressive one.

Two follow-on defects in the caps themselves were found and fixed before
release:

- **Padding defeated the BMP cap.** Measuring against the file length — or
  even the available span after `data_off` — let an attacker append junk to
  raise their own allowance. Appending 512 KB let the bomb through. The cap now
  measures the bytes the RLE stream **actually consumed**, the only denominator
  an attacker cannot inflate, which required the decoder to report it.
- **The GIF cap fired after the allocation it prevents.** It now runs before
  the index plane is allocated, and measures the gathered LZW bytes rather than
  the file length.

### A-5 · MEDIUM · GIF transparent index is a stale function-scoped var

`src/gif.cyr` — block walk.

A Graphic Control Extension applies to the graphic that follows it, so the last
one before the image descriptor governs — **including one that turns
transparency off**. `transparent` is function-scoped and was only ever set,
never cleared, so an earlier GCE's index survived a later GCE that revoked it,
keying pixels the file said were opaque.

This is precisely the Cyrius hazard the audit brief called out: `var` is
function-scoped, not block-scoped, and a value set in one branch persists.

**Repair.** The revoking case clears it explicitly.

### A-6 · LOW · GIF Graphic Control Extension block size never validated

`src/gif.cyr`.

The GCE's block size is fixed at 4 and every field after it was addressed by a
fixed offset — but nothing checked it. A GCE declaring another size had chitra
read the packed byte and the transparent index from bytes that are not those
fields.

**Repair.** The block size is checked; a mismatch rejects with
`CHITRA_ERR_GIF_HEADER`.

### A-7 · LOW · Sub-byte grayscale tRNS key compared at the wrong width

`src/png_color.cyr` — a gap in the 2026-08-23 H-1 repair.

H-1 made the depth-8/16 tRNS key a full-width compare; the **sub-byte**
grayscale path kept reading only the low byte. A key of `0x0105` names no 4-bit
sample (max 15), yet the low byte `5` aliased onto a real one and keyed those
pixels transparent.

**Repair.** Both bytes are assembled, so an out-of-range key matches nothing —
which is correct, since it names no pixel the image can contain. ImageMagick
reaches the same outcome by a different route: it warns *"tRNS chunk has
out-of-range samples for bit_depth"* and ignores the key.

### A-8 · LOW · tRNS ordering enforced two of the three rules its comment claimed

`src/png_filter.cyr` — a gap in the 2026-08-23 H-8 repair.

The comment has claimed since 0.3.3 that tRNS must be at-most-once, precede
IDAT, and — for a palette image — **follow PLTE**. The code enforced the first
two. tRNS entries are per-palette-entry alphas and mean nothing before the
palette they index exists (§ 5.6 / § 11.3.2).

**Repair.** Enforced. Note ImageMagick **tolerates** this ordering; chitra
rejects it, consistent with its posture elsewhere (it also rejects unknown
critical chunks per § 5.4, which many decoders skip).

### A-9 · LOW · LZW chain guard looser than the buffer it protected

`src/gif_lzw.cyr`.

The prefix-chain walk was bounded by a counter compared with `>`, permitting up
to 4097 stores into a 4096-byte buffer. Unreachable in practice — the maximum
real chain is ~4092 — but a guard one looser than its buffer is a latent
overflow, not a safe margin.

**Repair.** The bound is now on `sp` itself, the value that actually indexes
the buffer, checked before each store; the counter guard was tightened to `>=`
as well.

Two smaller items fixed alongside:

- **A doc/code contradiction.** The module header claimed a truncated LZW
  stream "rejects rather than zero-padding"; the decoder tolerates a missing
  End code, which real encoders omit. The header now describes what the code
  does, and names the amplification cap as what bounds the abuse case.
- **A wild pointer.** `srow = data + y * stride` was computed on the RLE path,
  where `stride` is meaningless, producing a pointer far past the input. Never
  dereferenced — the RLE branch reads its own index plane — but a pointer that
  survives only by never being used is latent, not safe.

## 4. Accepted risk

**A small PNG can legitimately decode to a large image, and no ratio cap can
change that.** A 2,116-byte 1-bit grayscale PNG declaring 4096×4096 decodes to
64 MB. The existing `CHITRA_MAX_INFLATE_RATIO` does not catch it because it
bounds *inflated:IDAT* (1021:1 here, under the cap) while the final RGBA is
32× the inflated scanlines.

This was reported as a finding, and it is **not** repaired, because the file is
a **complete, valid encoding of a solid image** — a genuinely solid 4096×4096
1-bit PNG really is ~2 KB and really is 64 MB decoded. The bomb and the
legitimate image are the same file shape, so a ratio cap would reject valid
PNGs.

That is exactly what distinguishes it from A-4: the GIF and BMP bombs supplied
*nothing* — 2 bytes of LZW, 4 bytes of opcodes — for 16.7 M pixels, where a
real solid image needs 13 KB and 137 KB respectively. Those caps separate
"supplies nothing" from "supplies a real encoding". No such line exists for
PNG.

The operative bound for PNG is therefore `CHITRA_MAX_PIXELS` (16,777,216 px →
64 MB per decode), which applies to every format. Consumers decoding untrusted
input in a long-running process should note that `chitra_image_free` is a
no-op and cost is cumulative — see
[architecture/003](../architecture/003-bump-allocator-no-free.md).

Every repair carries a regression test verified to fail against the pre-repair
code. Method notes worth carrying forward:

- **Reference cross-checking found what fuzzing could not.** Every
  wrong-output finding here (A-1, A-2, A-7) was confirmed by decoding the same
  bytes with ImageMagick. The fuzzers had run millions of cases over this code
  without flagging any of them, because none of them crash.
- **A guard that cannot fire is not a guard.** A-3 was a documented,
  CHANGELOG-claimed protection made unreachable by code a few lines above it.
  Worth checking, for any guard, that some input actually reaches it.
- **`var` is function-scoped in Cyrius**, and A-5 is what that costs. In a long
  decode function, a value set in one branch persists into every other.
